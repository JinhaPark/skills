# 원본·편집 이력 캐시와 비동기 병렬 처리

## 저장 구조와 식별자

- 프로젝트의 `docs/image-lineage.json`을 영속 대응표로 사용하라. 다른 프로젝트에서는 동등한 경로를 정하고 기록하라. 원본 바이트의 SHA-256을 sourceId로 사용하고 파일명은 별칭으로만 취급하라. 같은 이름·다른 바이트는 별개 원본이며, 같은 바이트·다른 이름은 같은 원본의 별칭이다.
- HEIC 디코딩·EXIF 회전·색공간 정규화 작업 사본은 별도 노드로 기록하고 원본 sourceId를 유지하라. 변환된 파일의 해시로 원본의 해시를 대체하지 말라. 유사 이미지 해시는 후보 검색에만 쓰고 캐시 적중으로 간주하지 말라.
- 편집 이력을 덮어쓰는 목록 대신 부모를 가리키는 불변 revision 그래프로 기록하라. 재편집은 실제 입력으로 사용한 revisionId를 parentRevisionId로 연결하라. 원본부터 다시 생성한 경우 parentRevisionId는 null로 두고 sourceId에 연결하라. 여러 입력·마스크·화풍 참고는 역할과 순서, 해시를 모두 기록하라.
- revision마다 revisionId, illustrationId, sourceId, parentRevisionId, operation, recipe, recipeKey, outputSha256, artifactRef, status, validation, createdAt을 저장하라. 시간·도구·모델·시드가 제공되지 않으면 null로 남기고 추측하지 말라. 프롬프트 전문과 사용 가능한 실제 도구 설정을 recipe에 보존하라.
- status는 queued/running/generated/validated/approved/failed/cancelled를 구분하라. 작업 완료와 사용자 승인은 다르며, approved는 실제 승인 근거가 있을 때만 기록하라. 기존 정상 게시본을 자동으로 사용자 승인작이라고 쓰지 말라.
- 게시 레코드에는 illustrationId, placement, activeRevisionId, WebP별 경로·해시·픽셀 크기·bytes·quality·최적화 키를 기록하라. 캡션·위치 변경은 게시 메타데이터만 바꾸고 그림을 다시 생성하지 말라. 직전 정상 게시본은 새 결과 검증 완료까지 유지하라.

## 두 단계 캐시 키와 적중 판정

1. UTF-8 JSON으로 recipe를 직렬화하라. 객체 키는 재귀적으로 정렬하고 공백 구분자는 `,`와 `:`만 사용하라. 배열 순서·프롬프트 문자열은 보존하라. 키 포맷 버전은 `travel-photo-cache-v1`로 포함하라.
2. 시각 편집 recipe에 원본 해시, 실제 부모 출력 해시, 순서 있는 입력/마스크/참고 해시와 역할, 정확한 프롬프트, 제거·보존 요소, 화풍·프레이밍, 실제 도구/모델/설정, 편집 규칙 버전을 포함하고 전체의 SHA-256을 visualKey로 사용하라. 알 수 없는 도구 정보는 null로 기록하되 서로 다른 제공자를 같은 값으로 합치지 말라.
3. 같은 visualKey라도 생성 결과가 다를 수 있다. recipeKey는 요청 식별자이고 outputSha256은 결과 식별자다. 재생성·다른 후보 요청에는 새 revisionId/attempt를 만들고 기존 결과를 지우지 말라. 여러 후보가 있으면 검증·선택 근거가 있는 결과를 고르라.
4. 최적화 recipe에는 선택한 출력 해시, 원본·편집본의 양축 제한, 폭 목록, 품질 시작/하한·단계, 용량 상한, 프레이밍, 메타데이터 정책, Pillow/WebP 버전과 최적화 스크립트 해시를 포함하라. 그 SHA-256을 optimizeKey로 사용하라. 인코더·폭·품질만 바뀌면 시각 편집을 재사용하고 WebP만 재생성하라.
5. 키 일치만으로 적중을 선언하지 말라. 실제 파일/영속 저장물 접근, 출력 해시, 디코딩, 크기·메타데이터·용량, 검증 상태와 공개 이용 조건을 확인하라. 실패/미완성/권리 미확인 결과는 게시하지 말라. 키가 없는 과거 자산은 legacy-verified 자산 재사용 후보이며 정확한 요청 캐시 적중은 아니다.
6. 원본·부모·프롬프트·참고·규칙 변경은 해당 시각 편집 및 그 하위 최적화 키만 무효화하라. 다른 원본은 유지하라. 공개 WebP가 남고 생성 마스터가 유실된 경우 WebP 재사용은 가능하지만, 고해상도 마스터가 있다고 주장하거나 확대 복원하지 말라.

## 보존과 기존 자료 이관

- Git에는 대응표와 공개 허용 WebP만 저장하라. 원본·생성 마스터·중간 수정본·민감 프롬프트는 사용 가능한 비공개 영속 저장소에 저장하고 대응표에는 공개해도 되는 식별자만 남기라. 개인 로컬 절대 경로·토큰·GPS는 커밋하지 말라. 민감 정보가 있으면 비공개 상세 레코드와 공개 요약을 분리하라.
- artifactRef는 임시 실행 경로가 아닌 실제 재조회 가능한 식별자로 기록하라. 영속 저장을 못 했으면 null과 missing/unpersisted 상태를 기록하라. 해시만 남긴 것은 원본 백업이 아니다. 파일은 해시를 확인한 후 사용하라.
- 기존 manifest·감사 기록·Git 이력에서 입증되는 사실만 이관하라. 원본 바이트가 없으면 sourceId/sourceSha256은 null, 과거 부모를 입증할 수 없으면 parentRevisionId는 null과 historyStatus: unknown을 기록하라. 파일명이나 외관으로 과거 해시·편집 순서를 만들어내지 말라.
- 사용 중인 revision과 부모·원본은 보존 대상으로 취급하라. 불필요 후보 정리는 참조 관계와 보존 필요를 확인한 별도 작업으로 수행하고 이번 실행에서 일괄 삭제하지 말라. 브라우저 서비스워커 캐시는 이 처리 캐시와 별개다.

## 여러 이미지의 비동기 서브에이전트 처리

- 독립 이미지가 2장 이상이고 서브에이전트 기능이 있으면 비동기로 병렬 할당하라. 먼저 캐시를 조회하고 동일 visualKey 요청은 하나의 작업으로 합치라. 적중 이미지를 다시 생성하려고 에이전트를 만들지 말라.
- 부모 에이전트가 작업 큐·키별 소유권·최종 대응표를 관리하라. 기본 동시 실행은 min(3, 사용 가능한 슬롯, 독립 미처리 작업 수)으로 시작하고 도구 한도·메모리·429 응답에 맞춰 줄이라. 사용 가능한 기능의 한도를 초과하지 말라.
- 이미지별 에이전트에 실제 입력과 해시, 실제 편집 부모, 화풍 참고, 제거·보존 지시, 적용 스킬/지침, 고유 출력 디렉터리와 jobId만 전달하라. 모든 대화 이력을 복제할 필요는 없다. 한 에이전트가 한 이미지의 생성→검증→최적화를 맡되 캐시 적중 단계는 생략하라.
- 서로 다른 이미지 작업은 먼저 모두 시작하고 완료 이벤트가 도착하는 대로 회수하라. 시작 직후 하나씩 기다려 직렬화하지 말라. 같은 이미지의 r1→r2와 생성→최적화는 의존성이므로 순서대로 실행하라. 독립 분기 후보만 병렬화하라.
- 서브에이전트는 자기 디렉터리의 자산과 결과 JSON만 작성하라. 공용 manifest·대응표·감사표·서비스워커·Git 브랜치·PR을 동시에 수정하거나 병합하지 말라. 공유 worktree에서 checkout을 바꾸지 말라. 분리 파일로 충분하지 않을 때만 별도 worktree를 사용하라.
- 반환값은 jobId, sourceId, parentRevisionId, recipeKey, 입력/출력 해시, 영속 참조, 변형 목록, 검증 결과, 실패 사유로 한정하라. 부모가 실제 파일·해시와 기준 revision이 여전히 최신인지 확인한 뒤 대응표와 manifest를 단독 작성하라. 오래된 부모 결과는 후보로 보존하고 최신 결과를 덮어쓰지 말라.
- 동일 키의 중복 실행을 큐에서 차단하라. 여러 세션이 겹치면 기준 Git SHA/activeRevisionId를 비교하고 불일치 시 다시 읽어 병합하라. 파일별 결과를 먼저 완성하고 부모가 임시 파일→원자적 교체로 대응표를 게시하라. 중단된 running은 소유 작업의 생존·부분 결과를 확인한 뒤 재큐잉하라.
- 타임아웃은 실패 확정이 아니므로 기존 생성 요청의 완료·결과를 먼저 확인하고 중복 요청을 피하라. 일시 실패는 최대 2회 재시도하고 제공된 Retry-After를 따르라. 한 이미지 실패로 성공한 다른 이미지를 재생성하지 말라. 영속 참조·큐 상태를 남겨 재개하라. 실패한 교체는 기존 게시본을 유지하라.
- 서브에이전트 기능이 없거나 이미지 도구가 동시 실행을 지원하지 않으면 가능한 준비·검증만 병렬화하고 생성은 순차 수행하라. 제약과 실제 처리 방식을 보고하고 병렬 실행을 꾸미지 말라.

- 게시 교체 시 콘텐츠 해시/revision을 포함한 새 파일명을 우선 사용하라. 기존 경로 유지가 필요한 프로젝트는 서비스워커 갱신·이전 캐시 전환을 검증하라.
